# Architecture Decisions — «Размерно»

Дата актуализации: 2026-06-10

## ADR-001 — Цена считается точной

**Дата:** 2026-06-10  
**Решение:** В интерфейсе цена показывается как точная, а не предварительная.  
**Причина:** Пользователь должен доверять расчёту перед заявкой.  
**Последствия:** Запрещены формулировки “примерно”, “ориентировочно”, “предварительно” в активном сценарии цены. Любые warning не должны подрывать точность цены.

## ADR-002 — Дилерский прайс умножается на коэффициент ×1.3

**Дата:** 2026-06-10  
**Решение:** Клиентская цена = цена из прайса × 1.3.  
**Причина:** Это утверждённое коммерческое правило по загруженному дилерскому прайсу.  
**Последствия:** Pricing QA должен проверять коэффициент; любые новые price source должны явно учитывать это правило.

## ADR-003 — 3D является основным режимом конструктора

**Дата:** 2026-06-10  
**Решение:** 3D открывается по умолчанию и является главным рабочим интерфейсом.  
**Причина:** Продуктовая идея — пользователь собирает мебель на модели.  
**Последствия:** Новые действия наполнения должны проектироваться от selected zone в 3D, а не от глобальных form counters.

## ADR-004 — 2D является fallback, а не полноценным инженерным чертежом

**Дата:** 2026-06-10  
**Решение:** Сейчас 2D — рабочий fallback без декоров и без production-level чертежа.  
**Причина:** Нужно обеспечить сценарий без WebGL, но не раздувать scope.  
**Последствия:** Полный blueprint/export/dimension chains откладываются.

## ADR-005 — Конструктор имеет 4 шага

**Дата:** 2026-06-10  
**Решение:** Сохраняются шаги: Размеры / Наполнение / Материалы / Заявка.  
**Причина:** Это достаточно простой и понятный wizard для MVP.  
**Последствия:** Новые функции должны встраиваться в эти шаги, а не создавать новые ветки без решения.

## ADR-006 — Наполнение управляется через выбранную зону

**Дата:** 2026-06-10  
**Решение:** В обычном режиме пользователь выбирает зону на модели и добавляет наполнение туда.  
**Причина:** Глобальные счётчики не отвечают на вопрос “где именно”.  
**Последствия:** Полки/ящики/штанга не должны возвращаться как основной global control в обычном режиме.

## ADR-007 — В UI используется термин “зона”, в коде временно допустим `compartment`

**Дата:** 2026-06-10  
**Решение:** Пользовательская терминология — “зона”; внутренний legacy term `compartment` сохраняется как compatibility layer.  
**Причина:** Полный rename опасен для geometry/validation/tests.  
**Последствия:** Новые UI-тексты используют “зона”; технический rename делать отдельным refactor-этапом.

## ADR-008 — Фасады в обычном режиме управляются на уровне секций

**Дата:** 2026-06-10  
**Решение:** Обычный режим: фасады на уровне секции.  
**Причина:** Это проще для массового пользователя.  
**Последствия:** Не показывать управление фасадами каждой зоны в обычном режиме.

## ADR-009 — Фасады по зонам доступны только в точной настройке

**Дата:** 2026-06-10  
**Решение:** В exact mode можно управлять фасадами отдельных зон.  
**Причина:** Это расширенная логика для опытного пользователя.  
**Последствия:** Exact mode должен быть глобальным toggle и действовать на все шаги.

## ADR-010 — Warning и error разделены

**Дата:** 2026-06-10  
**Решение:** Blocking error блокирует действие; warning предупреждает; сложные production warnings скрываются от клиента.  
**Причина:** Warning не должен выглядеть как поломка продукта.  
**Последствия:** Validation UI должен привязывать проблему к месту и давать auto-fix там, где возможно.

## ADR-011 — Autosave отложен

**Дата:** 2026-06-10  
**Решение:** Autosave/local draft/cloud draft не входят в ближайший MVP.  
**Причина:** Это не критично сейчас и может усложнить PII/consistency.  
**Последствия:** Не сохранять PII/local draft; reset и success state должны работать без autosave.

## ADR-012 — Checkout остаётся внутри конструктора

**Дата:** 2026-06-10  
**Решение:** Заявка оформляется внутри конструктора.  
**Причина:** Это финальный шаг текущего MVP flow.  
**Последствия:** Checkout должен читать тот же constructor state и pricing snapshot, без отдельной параллельной логики.

## ADR-013 — После отправки заявки модель не сбрасывается

**Дата:** 2026-06-10  
**Решение:** Success state не должен reset-ить конфигурацию.  
**Причина:** Пользователь может хотеть сохранить результат или повторить действие.  
**Последствия:** Reset — отдельное явное действие с подтверждением.

## ADR-014 — Legacy не удаляется без миграции тестов

**Дата:** 2026-06-10  
**Решение:** `src/configurator/**` остаётся в quarantine до миграции test-backed сценариев.  
**Причина:** Слепое удаление снижает regression confidence.  
**Последствия:** Новые imports из legacy запрещены; удаление — отдельный этап.

## ADR-015 — CSS cleanup делается после визуального QA

**Дата:** 2026-06-10  
**Решение:** Не делать агрессивный CSS purge без проверки финального UI.  
**Причина:** Stage-слои могут перекрывать друг друга; случайное удаление сломает внешний вид.  
**Последствия:** Сначала карта классов и визуальный QA, потом cleanup.
