# Agent Workflow — Размерно

Документ задаёт обязательный порядок работы агентов.

---

## 1. Что читать перед началом задачи

Каждый агент обязан сначала прочитать:

1. `docs/planning/README.md`
2. `docs/planning/master-development-plan-v1.md`
3. `docs/planning/current-backlog.md`
4. `docs/planning/mvp-scope.md`
5. `docs/planning/architecture-decisions.md`
6. `docs/planning/parallelization-rules.md`
7. `docs/planning/release-roadmap.md`
8. `docs/audit/documentation-audit-v1.md`
9. `docs/audit/architecture-audit-v1.md`
10. `docs/agent/architect-rules.md`

Если задача относится к pricing, production, checkout, Supabase, API или admin, агент обязан дополнительно найти и прочитать профильные документы в `docs/`.

---

## 2. Обязательный рабочий цикл

1. Audit — изучить текущие файлы и зависимости.
2. Plan — сформировать конкретный план изменения.
3. Implementation — менять только файлы в scope.
4. QA — запустить релевантные проверки.
5. Report — описать результат, риски и backlog.

---

## 3. Запрещено агентам

- имитировать прогресс;
- писать «готово», если файлы не изменены и проверки не выполнены;
- делать редизайн без прямого задания;
- менять pricing без отдельного разрешения;
- менять order flow без отдельного разрешения;
- менять API/Supabase/admin без отдельного разрешения;
- удалять legacy-код без плана миграции тестов;
- делать массовое переименование без необходимости;
- смешивать несколько крупных задач в один неконтролируемый этап;
- добавлять post-MVP функции в MVP scope.

---

## 4. Формат отчёта после задачи

Агент обязан вернуть:

- что планировалось;
- что сделано;
- какие файлы изменены;
- какие проверки запущены;
- какие проверки прошли;
- какие проверки не прошли;
- известные риски;
- что добавить в backlog;
- что нельзя делать следующим агентам без проверки.

---

## 5. Правила изменения документов

Если агент изменил архитектуру, state, pricing, checkout, production или MVP scope, он обязан обновить соответствующий planning-документ.

Если решение пользователя изменило предыдущие правила, агент обязан:

1. зафиксировать новое решение;
2. указать, какое старое решение оно заменяет;
3. обновить backlog или roadmap.

---

## 6. Правила работы с Git

Рекомендуемый порядок:

1. отдельная ветка под задачу;
2. маленькие commits;
3. понятные commit messages;
4. pull request с кратким отчётом;
5. не смешивать документацию, UI, pricing и production в одном PR без необходимости.

Если задача выполняется напрямую в main, она должна быть только документационной или явно безопасной.

---

## 7. Минимальные проверки

Для кодовых задач минимум:

- `npm run typecheck`;
- `npm run build`.

Для pricing:

- профильные pricing tests;
- проверка ключевых сценариев цены.

Для constructor:

- typecheck;
- build;
- relevant constructor tests;
- smoke test маршрута конструктора.

Для docs-only задач проверки сборки не обязательны, если не менялись package/config/source файлы.
