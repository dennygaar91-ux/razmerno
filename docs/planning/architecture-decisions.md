# Architecture Decisions — Размерно

Документ фиксирует ключевые решения, которые новые агенты не должны переоткрывать без прямого запроса пользователя.

---

## Product Decisions

1. Проект «Размерно» — онлайн-конструктор корпусной мебели под размер.
2. MVP должен соединять простоту конструктора и точность мебельного конфигуратора.
3. Основной пользователь — обычный человек без опыта, но DIY-пользователь тоже должен получить расширенные возможности.
4. Главный conversion goal MVP — заявка.
5. Личный кабинет клиента не входит в MVP.
6. Отзывы и фейковые social proof не добавлять.
7. Кухни не трогать до post-MVP.

---

## Constructor Decisions

1. Основной активный путь — новый Constructor3D.
2. Старый Constructor держать в quarantine до безопасной миграции/удаления.
3. 3D открывается по умолчанию.
4. 2D нужен как fallback, но полноценный инженерный чертёжный 2D можно отложить.
5. WebGL fallback обязателен.
6. Шаги конструктора: Размеры / Наполнение / Материалы / Заявка.
7. Тип мебели находится внутри шага Размеры.
8. Checkout остаётся внутри конструктора.
9. Цена показывается как точная.
10. Warning блокирует заявку только если он blocking warning/error.
11. Success после отправки заявки не должен сбрасывать модель.
12. Autosave можно отложить, если он не требуется для ближайшего MVP.

---

## Zones / Sections / Filling Decisions

1. В интерфейсе использовать термин «Зона».
2. В коде допустимо временно сохранять термин `compartment`, если массовое переименование опасно.
3. Пользователь сначала выбирает секцию/зону на 3D-модели.
4. После выбора появляется контекстное действие/меню.
5. Кнопка `+` открывает меню, но не добавляет элемент сразу.
6. Полка добавляется внутри выбранной зоны и делит её на две зоны.
7. Высота полки в обычном режиме считается от низа выбранной зоны.
8. Фасады в обычном режиме управляются на уровне секции.
9. Фасады по отдельным зонам доступны в точной настройке.
10. Удаление наполнения должно быть на уровне конкретного элемента.
11. Random preset должен применять простой рабочий пресет, а не быть пустой заглушкой.

---

## Three.js Decisions

1. 3D должен быть реалистичным мебельным preview.
2. Материал в 3D должен соответствовать выбранному декору.
3. Использовать реальные текстуры материалов, когда они доступны.
4. Показывать фурнитуру максимально полно в рамках MVP: петли, направляющие, штангу, ручки, крепёж — поэтапно.
5. Камеры: свободно, спереди, сбоку, сверху.
6. 2D fallback должен позволять продолжить конфигурацию.
7. Глубокую Three.js optimization можно переносить после MVP, если базовая сцена стабильна.
8. Cinematic animation не входит в обязательный MVP.

## Pricing Decisions

1. Цена должна быть точной, не предварительной.
2. Клиент и сервер должны использовать один источник правил или полностью согласованную модель расчёта.
3. По дилерскому прайсу применяется коэффициент x1.3.
4. ЛДСП/МДФ в прайсе указаны за 1 кв.м с учётом присадки и распила, если это подтверждено актуальным прайсом.
5. Отдельно учитывать кромку, кромление и упаковку, если они выделены в прайсе.
6. Доставка внутри МКАД: 6000 ₽.
7. За пределами МКАД: +50 ₽/км.
8. Сборка: +10% от стоимости шкафа без учёта доставки.

---

## Checkout / Orders Decisions

1. Клиент обязан указать телефон.
2. Email обязателен.
3. Телефон — RU format.
4. При включённой доставке адрес обязателен.
5. Если письмо клиенту не ушло, но заявка менеджеру ушла, заявка считается успешной.
6. Ошибки email-отправки нужно логировать без персональных данных.
7. PII не хранить в localStorage.
8. После отправки заявки модель не reset-ить.
9. Повторная отправка — с защитой от частого submit.

---

## Production Decisions

1. Сложная production logic остаётся под капотом.
2. Клиенту показывать только понятные ошибки и предупреждения.
3. В админке нужна профессиональная проверка.
4. Production model должен хранить версии и ревизии.
5. Basis integration — после базового MVP, сначала JSON для ручного сценария.
6. Автоматическая `.b3d` generation — post-MVP.

---

## Design / UX Decisions

1. Стиль: 70% calm premium / Apple-like и 30% тёплая модульность.
2. Lego-метафору использовать аккуратно: понятный конструктор, но не игрушечность.
3. Оранжевый — брендовый UI-акцент, не материал.
4. Интерфейс должен быть менее шумным и более сфокусированным.
5. Не делать глобальный CSS cleanup без этапности.
6. Стандартизировать дизайн-систему последовательно от блока к блоку.
