# Protected Zones — «Размерно»

Дата: 2026-06-13
Тип: architecture boundary document.

## Цель

Документ фиксирует зоны проекта, которые нельзя менять без отдельного задания и отдельной проверки. Это снижает риск случайных регрессов при работе LLM-агентов и при долгосрочной разработке.

## Абсолютно защищенные зоны

До отдельного письменного задания запрещено менять:

- pricing engine;
- order flow;
- checkout logic;
- отправку заявок;
- Supabase integration;
- API routes;
- backend / Vercel Functions;
- admin panel;
- export logic;
- production export layer.

## Запрещенные типы изменений

Без отдельного задания нельзя делать:

- редизайн;
- UX-перестройку;
- Three.js-переработку;
- новые функции;
- изменение бизнес-логики расчета;
- изменение формы заявки;
- изменение контрактов API;
- миграции Supabase;
- удаление runtime-кода.

## Разрешенные изменения в архитектурном этапе

Разрешено:

- создавать и обновлять документацию;
- создавать ADR;
- описывать границы модулей;
- описывать QA-матрицы;
- описывать CI-policy;
- добавлять документационные backlog-файлы;
- добавлять scripts только для read-only аудита, если они не влияют на runtime.

## Правило проверки

Любой агент перед изменением файла должен определить:

1. относится ли файл к protected zone;
2. изменяет ли правка runtime-поведение;
3. требуется ли отдельное разрешение пользователя;
4. есть ли QA-команда для проверки.

Если есть сомнение, правку не выполнять и запросить подтверждение.

## Примеры protected paths

- `api/**`
- `src/pricing/**`
- `src/shared/lib/pricing-core.ts`
- `src/constructor/production/**`
- `src/admin/**`
- `src/configurator/**` при изменениях поведения конструктора
- `supabase/**`
- `scripts/*price*`
- `scripts/*production*`

## Принцип отчетности

В каждом отчете нужно отдельно писать:

- что реально изменено в GitHub;
- что подготовлено, но не закоммичено;
- что не выполнено;
- причину невыполнения.
