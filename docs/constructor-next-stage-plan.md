# Constructor next stage plan

Документ фиксирует развилку следующего этапа после стабилизации frontend конструктора.

## Текущая ситуация

Frontend почти доведён до pre-MVP состояния. Следующий крупный этап нужно выбрать осознанно, потому что оба направления важные:

1. Three.js viewer.
2. Backend-калькулятор и правила расчёта.

## Вариант A. Three.js viewer

### Что это

Замена текущего CSS-preview шкафа на реальный 3D viewer на Three.js / React Three Fiber.

### Зачем нужно

Пользователь будет лучше понимать шкаф:

- размеры;
- секции;
- полки;
- ящики;
- штангу;
- материал;
- активную секцию.

Это повышает доверие и делает продукт похожим на настоящий конструктор, а не на форму расчёта.

### Что делать

1. Установить зависимости:

```bash
npm install three @react-three/fiber @react-three/drei
```

2. Создать компонент:

```txt
src/components/constructor/three/CabinetCanvas3D.jsx
```

3. Подключить его через существующий `renderCanvas(sceneProps)`.

4. Использовать контракт:

```txt
docs/threejs-viewer-contract.md
```

5. На первом этапе построить простую геометрию:

- корпус;
- вертикальные перегородки;
- полки;
- ящики простыми box-элементами;
- штангу цилиндром;
- подсветку active section.

6. Сохранить React UI вне Canvas:

- toolbar;
- quick actions;
- section map;
- forms;
- summary.

### Что получим в конце

- реальный 3D-preview;
- визуальную связь между настройками и шкафом;
- возможность дальше подключить текстуры материалов;
- основу для будущей деталировки.

### Риски

- можно быстро раздуть bundle;
- можно получить плохую производительность;
- без backend-правил 3D будет красивым, но не технологически точным;
- нужно аккуратно работать с responsive высотой viewer.

### Когда выбирать этот путь

Выбирать, если цель ближайшего этапа:

```txt
сделать продукт визуально убедительным для пользователя / инвестора / тестовых клиентов
```

## Вариант B. Backend-калькулятор и правила расчёта

### Что это

Вынос расчёта стоимости, правил ограничений, спецификации и будущей деталировки из frontend в backend/domain layer.

### Зачем нужно

Сейчас frontend умеет считать предварительно, но настоящий мебельный конструктор должен иметь правила:

- материалы;
- кромка;
- фурнитура;
- крепёж;
- присадка;
- ограничения;
- стоимость услуг;
- упаковка;
- доставка;
- наценка;
- НДС;
- экспорт под БАЗИС.

### Что делать

1. Зафиксировать domain model:

```txt
Project
Cabinet
Section
Filling
Material
Edge
Hardware
Service
Estimate
Part
Drilling
Order
```

2. Создать backend/core calculation module.

Возможные пути:

```txt
Node.js service внутри проекта
или отдельный package/core
```

3. Перенести правила расчёта из frontend:

```txt
constructorPricing.js → backend/domain calculation
```

4. Frontend оставить только отображением.

5. Подготовить JSON contract:

```txt
frontend project → backend estimate request → estimate response
```

6. Подготовить базовые rules:

- ЛДСП 16 мм;
- кромка ABS 0.8 / 2 мм;
- полки;
- ящики;
- штанга;
- ручки / tip-on;
- Hettich / Firmax MVP;
- распил;
- кромление;
- присадка;
- доставка;
- ручная наценка.

### Что получим в конце

- более честный расчёт;
- основу для production логики;
- возможность подключить админку цен;
- возможность генерировать спецификацию;
- более правильный путь к БАЗИС-Мебельщик.

### Риски

- пользователь визуально не увидит большого улучшения;
- нужен более строгий технический дизайн;
- потребуется больше тестов;
- можно застрять в сложной логике до визуального MVP.

### Когда выбирать этот путь

Выбирать, если цель ближайшего этапа:

```txt
сделать продукт технологически правильным и подготовить реальный расчёт заказов
```

## Моя рекомендация

Лучший порядок:

```txt
1. Сначала стабилизировать frontend после build/QA.
2. Затем сделать минимальный Three.js viewer, но без сложной технологической логики.
3. После этого перейти к backend-калькулятору.
```

Почему так:

- frontend уже почти готов;
- пользователю нужен визуальный wow/доверие;
- текущий contract под Three.js уже подготовлен;
- минимальный Three.js viewer даст быстрый эффект;
- backend-калькулятор лучше делать после того, как визуальный сценарий зафиксирован.

## Рекомендуемый следующий этап

```txt
Этап 13. Minimal Three.js Viewer
```

### Цель

Заменить CSS mockup на простой, стабильный 3D viewer без production-деталировки.

### Scope

Входит:

- Three.js/R3F setup;
- CabinetCanvas3D;
- корпус box geometry;
- секции;
- полки;
- ящики;
- штанга;
- active section highlight;
- material tone;
- orbit controls с ограничениями;
- fallback на CSS preview.

Не входит:

- реальные текстуры;
- точная деталировка;
- присадка;
- экспорт в БАЗИС;
- backend prices;
- mobile optimization;
- сложная физика/анимации.

### Готовность в конце

```txt
Frontend constructor + minimal 3D preview — demo-ready pre-MVP
```

## После Three.js

Следующий этап:

```txt
Этап 14. Backend calculation core
```

Scope:

- estimate API contract;
- domain model;
- pricing rules;
- validation rules;
- material/hardware catalog shape;
- preparation for admin panel;
- preparation for БАЗИС JSON export.

## Что делать прямо сейчас

До выбора следующего этапа:

1. Выполнить build.
2. Пройти manual QA.
3. Сделать финальные скриншоты.
4. Зафиксировать accepted frontend state.
5. После этого начать Этап 13.
