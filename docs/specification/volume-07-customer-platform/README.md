# RPES — Том VII. Customer Platform

Проект: «Размерно»  
Версия: 1.1 draft  
Статус: рабочий Source of Truth по авторизации и личному кабинету  
Дата: 2026-06-25  

---

# 1. Назначение тома

Том VII описывает клиентскую платформу «Размерно»: авторизацию, личный кабинет, проекты, заявки, статусы, историю, сохранение конфигураций и клиентское представление заказа.

Личный кабинет становится обязательной частью продукта. Он закрывает полный пользовательский цикл: пользователь не просто отправляет заявку, а получает пространство, где может видеть свои проекты, статусы, параметры, стоимость и историю.

---

# 2. Роль клиентской платформы

Клиентская платформа нужна для трёх целей:

1. Не потерять конфигурацию пользователя.
2. Связать заявку с конкретным пользователем.
3. Дать пользователю прозрачность после отправки заявки.

Без личного кабинета продукт остаётся разовой формой заявки. С личным кабинетом он становится полноценным сервисом.

---

# 3. Авторизация

## 3.1 Главный принцип

Авторизация не должна требоваться заранее.

Пользователь должен иметь возможность открыть конструктор и собрать мебель без регистрации.

Авторизация требуется только после нажатия «Отправить заявку».

## 3.2 Почему так

Ранняя авторизация повышает friction и мешает пользователю быстро понять ценность продукта.

Главная цель — сначала дать пользователю собрать мебель и увидеть ценность, затем попросить авторизацию для сохранения заявки.

## 3.3 Сценарий для неавторизованного пользователя

```text
Пользователь собрал конфигурацию
→ нажал «Отправить заявку»
→ система проверила авторизацию
→ пользователь не авторизован
→ система сохраняет конфигурацию
→ пользователь проходит авторизацию
→ система возвращает пользователя к конфигурации
→ создаётся заявка
→ пользователь видит номер заявки
→ пользователь переходит в личный кабинет
```

## 3.4 Сценарий для авторизованного пользователя

```text
Пользователь собрал конфигурацию
→ нажал «Отправить заявку»
→ система проверила авторизацию
→ пользователь авторизован
→ создаётся заявка
→ пользователь видит номер заявки
→ пользователь переходит в личный кабинет
```

## 3.5 Инварианты авторизации

1. Конфигурация не теряется.
2. Авторизация не требуется до отправки заявки.
3. После авторизации пользователь возвращается к своей конфигурации.
4. Заявка связана с пользователем.
5. Пользователь попадает в личный кабинет после создания заявки.

---

# 4. Личный кабинет

## 4.1 Назначение

Личный кабинет — клиентская зона, где пользователь видит свои проекты, заявки, статусы и информацию о заказах.

## 4.2 MVP-состав личного кабинета

В MVP личный кабинет должен содержать:

- список проектов;
- список заявок;
- карточку заказа;
- номер заявки;
- статус;
- стоимость;
- размеры;
- материалы;
- наполнение;
- доставку;
- сборку;
- историю изменений;
- клиентскую версию production summary.

## 4.3 Что не входит в MVP личного кабинета

На первом этапе можно не делать:

- сложный профиль пользователя;
- оплату;
- чат с менеджером;
- push-уведомления;
- документы для бухгалтерии;
- полноценный повторный заказ;
- публичный sharing проекта.

Эти функции могут быть post-MVP.

---

# 5. Проекты

## 5.1 Что такое проект

Проект — сохранённая конфигурация мебели, которую пользователь создал в конструкторе.

Проект может быть:

- черновиком;
- отправленной заявкой;
- заказом в проверке;
- заказом в производстве;
- закрытым заказом.

## 5.2 Проект и заявка

Проект и заявка не одно и то же.

Проект — конфигурация мебели.

Заявка — событие отправки валидной конфигурации в обработку.

Одна конфигурация может стать заявкой. В будущем возможно создание новой версии проекта на основе старой заявки.

## 5.3 Что хранит проект

Проект должен хранить:

- тип мебели;
- размеры;
- секции;
- наполнение;
- материалы;
- выбранную фурнитуру;
- опоры;
- пользовательские настройки;
- preview;
- актуальный статус;
- ссылку на production model snapshot;
- ссылку на price snapshot.

---

# 6. Заявки

## 6.1 Что такое заявка

Заявка — валидная конфигурация, отправленная пользователем после проверки авторизации.

Заявка должна быть полностью воспроизводимой.

## 6.2 Что хранит заявка

Заявка хранит:

- номер заявки;
- user id;
- project id;
- дату создания;
- статус;
- конфигурацию;
- price snapshot;
- production model snapshot;
- contact data;
- delivery/assembly settings;
- email status;
- revision history.

## 6.3 Номер заявки

После создания заявки пользователь должен видеть номер заявки.

Номер заявки должен быть доступен в личном кабинете и email.

---

# 7. Статусы клиента

## 7.1 Клиентские статусы

Клиенту нужны понятные статусы, не перегруженные внутренней операционной логикой.

Рекомендуемые клиентские статусы:

- заявка создана;
- на проверке;
- в производстве;
- отправлено;
- закрыто.

## 7.2 Отличие от админских статусов

Админские статусы могут быть более детальными, но клиенту показывается упрощённый и понятный статус.

## 7.3 Что нельзя показывать клиенту

Клиент не должен видеть:

- internal validation codes;
- production warnings;
- Basis internal status;
- raw JSON;
- stack traces;
- technical failure reasons.

---

# 8. Карточка заказа

## 8.1 Что должно быть в карточке

Карточка заказа должна показывать:

- номер заявки;
- дату;
- статус;
- тип мебели;
- размеры;
- материалы;
- наполнение;
- стоимость изделия;
- доставка;
- сборка;
- итоговая сумма;
- основные параметры;
- понятный preview.

## 8.2 Что можно показывать как production summary

Клиенту можно показывать:

- «Модель подготовлена»;
- «Проверка конфигурации пройдена»;
- «Комплект деталей сформирован»;
- «Данные переданы на проверку».

Нельзя показывать:

- карту присадки;
- кромку;
- пазы;
- raw Basis JSON;
- внутренние warnings.

---

# 9. История изменений

## 9.1 Зачем нужна история

История нужна, чтобы пользователь и админ могли понять, что происходило с заказом.

## 9.2 Что показывать клиенту

Клиенту можно показывать:

- заявка создана;
- статус изменён;
- заказ перешёл в производство;
- заказ отправлен;
- заказ закрыт.

## 9.3 Что скрывать

Не показывать клиенту:

- технические правки production model;
- internal review notes;
- validation details;
- raw JSON diffs.

---

# 10. Клиентская версия Production Summary

## 10.1 Назначение

Production Summary для клиента должен давать уверенность, что система правильно подготовила заказ, но не раскрывать техническую сложность.

## 10.2 Что можно показывать

- тип мебели;
- размеры;
- материалы;
- состав комплекта в понятном виде;
- количество основных элементов;
- статус проверки;
- статус подготовки.

## 10.3 Что нельзя показывать

- присадку;
- кромку;
- пазы;
- drilling coordinates;
- Basis internal plan;
- raw JSON;
- технологические warnings.

---

# 11. Сохранение конфигурации

## 11.1 Главный инвариант

Конфигурация не должна теряться.

Особенно важно:

- до авторизации;
- во время авторизации;
- после возврата из авторизации;
- после создания заявки.

## 11.2 Что должно сохраняться

- тип мебели;
- размеры;
- секции;
- наполнение;
- материалы;
- panel-level overrides;
- фурнитура;
- опоры;
- delivery/assembly choices;
- price snapshot после заявки;
- production snapshot после заявки.

## 11.3 Autosave

Полноценный autosave может быть отдельной задачей, но логика сохранения при авторизации и отправке заявки обязательна.

---

# 12. Уведомления

## 12.1 Email

После заявки пользователь должен получить email с номером заказа и краткой информацией.

## 12.2 Что должно быть в email

- номер заявки;
- краткое подтверждение;
- ссылка в личный кабинет;
- базовая информация о заказе.

## 12.3 Что нельзя отправлять

- raw JSON;
- технические ошибки;
- production internals.

---

# 13. Связь с Constructor

Личный кабинет получает данные из конструктора через сохранённую конфигурацию и snapshots.

Конструктор должен уметь:

- сохранить конфигурацию перед авторизацией;
- восстановить конфигурацию после авторизации;
- создать проект/заявку;
- передать данные в личный кабинет.

---

# 14. Связь с Pricing

Личный кабинет показывает price snapshot.

Если цена в каталоге изменилась позже, исторический заказ должен показывать цену, актуальную на момент заявки.

---

# 15. Связь с Production JSON

Личный кабинет хранит ссылку на production model snapshot, но не показывает raw production JSON клиенту.

Клиент видит только клиентское summary.

---

# 16. Связь с Admin

Админка и личный кабинет должны смотреть на одну заявку, но показывать разный уровень детализации.

Клиентский вид — простой.

Админский вид — операционный и технический.

---

# 17. Инварианты Customer Platform

1. Авторизация после попытки отправки заявки.
2. Конфигурация не теряется.
3. Личный кабинет обязателен для MVP.
4. Заявка связана с пользователем.
5. Проект и заявка различаются.
6. Price snapshot сохраняется.
7. Production snapshot сохраняется.
8. Клиент не видит raw JSON.
9. Клиент не видит production details.
10. Email содержит номер заявки и ссылку в кабинет.
11. Историческая цена не меняется после изменения каталога.
12. Клиентский статус проще админского.

# 20. Дополнительные решения Customer Platform v1.1

## 20.1 Авторизация

Для MVP/Release v1 используется авторизация:

- email;
- пароль.

Magic link, SMS, соцсети и другие варианты не входят в текущий scope.

## 20.2 Черновики

Черновики нужны.

Ограничение:

- не более 3 черновиков на пользователя.

Если пользователь достигает лимита, система должна предложить удалить или заменить один из существующих черновиков.

## 20.3 Редактирование после заявки

Пользователь не редактирует отправленную заявку напрямую.

Вместо этого в карточке проекта/заявки должна быть кнопка:

> Связаться с менеджером

Корректировки после отправки заявки происходят через менеджера.

## 20.4 Кнопка «Повторить»

В карточке проекта должна быть кнопка:

> Повторить

Она создаёт новую конфигурацию на основе существующего проекта/заказа.

Повтор не должен изменять исходный заказ.

## 20.5 Карточка проекта

В карточке проекта должны быть минимум две важные кнопки:

- «Связаться с менеджером»;
- «Повторить».

## 20.6 История корректировок

Если корректировка происходит через менеджера, это должно отражаться в истории заказа/проекта.
