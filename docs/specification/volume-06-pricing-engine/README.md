# RPES — Том VI. Pricing Engine

Проект: «Размерно»  
Версия: 1.1 draft  
Статус: рабочий Source of Truth по Pricing  
Дата: 2026-06-25  

---

# 1. Назначение тома

Том VI описывает продуктовую и инженерную логику расчёта стоимости в «Размерно».

Pricing Engine должен обеспечивать точную стоимость изделия, согласованную с конструктором, материалами, Production JSON, Supabase catalog, заявкой, личным кабинетом и админкой.

Главная задача Pricing Engine:

> Клиент видит точную стоимость изделия, а система сохраняет воспроизводимый price snapshot для заказа.

---

# 2. Главный принцип Pricing

Цена должна быть точной.

Формулировка «предварительная цена» не соответствует текущему продуктовому решению.

Цена может быть пересчитана при изменении конфигурации, но в момент отправки заявки она должна быть точной для сохранённой конфигурации и текущих правил расчёта.

---

# 3. Что входит в стоимость изделия

В стоимость изделия входят:

- материалы корпуса;
- материалы фасадов;
- ХДФ;
- кромка;
- фурнитура;
- полкодержатели;
- направляющие;
- петли;
- ручки / push-to-open;
- опоры;
- упаковка;
- производственные составляющие, которые относятся к изготовлению комплекта.

Не входят в стоимость изделия:

- доставка;
- сборка.

Доставка и сборка считаются отдельными строками.

---

# 4. Что показывать клиенту

Клиенту нужно показывать простую детализацию:

- стоимость изделия;
- доставка, если выбрана;
- сборка, если выбрана;
- итоговая сумма.

Не нужно показывать:

- стоимость каждой панели;
- стоимость каждой кромки;
- стоимость каждой петли;
- стоимость каждой направляющей;
- внутреннюю производственную калькуляцию.

Причина: клиент должен понимать стоимость, но не погружаться в производство.

---

# 5. Что показывать администратору

Администратор должен видеть больше деталей, чем клиент.

Админке нужны:

- цена изделия;
- доставка;
- сборка;
- итоговая сумма;
- client price;
- server price;
- расхождение client/server, если есть;
- source of price;
- price snapshot;
- pricing warnings, если они внутренние;
- breakdown по крупным категориям.

Админке не обязательно на первом этапе показывать каждый винт или каждую операцию, но данные должны быть доступны в price snapshot.

---

# 6. Источник цены

## 6.1 Supabase catalog

Supabase должен стать runtime catalog.

В будущем Supabase должен хранить максимально всё:

- материалы;
- размеры листов;
- декоры;
- толщины;
- цены;
- фурнитуру;
- характеристики;
- упаковку;
- возможно услуги.

## 6.2 Seed fallback

Seed fallback допустим для разработки и аварийного режима, но не должен быть финальным production source.

## 6.3 Source lock

Система должна явно понимать, откуда пришла цена:

- Supabase;
- seed fallback;
- другой будущий источник.

Цена не должна выглядеть одинаково для системы, если источник разный.

---

# 7. Материалы и листы

## 7.1 Материалы

Pricing должен учитывать:

- ЛДСП 16 мм;
- МДФ 18 мм;
- ХДФ 3 мм;
- декор;
- производитель;
- цену за м²;
- размер листа;
- коэффициент.

## 7.2 Размеры листов

Размеры листов должны храниться в Supabase.

Это важно для будущего:

- оптимизации раскроя;
- проверки доступности;
- расчёта отходов;
- более точной себестоимости.

На текущем этапе остатки не учитываются.

## 7.3 Коэффициент

Ранее зафиксировано правило:

```text
клиентская цена = цена из прайса × 1.3
```

Это правило должно быть отражено в pricing policy, пока не будет заменено новой коммерческой моделью.

---

# 8. Нестандартные размеры

В продуктовой логике не должно быть категории «нестандартный размер».

Причина:

мебель моделируется через допустимые секции.

Если секции находятся в допустимых пределах, изделие является валидным.

Если секции выходят за пределы, конфигурация невалидна и не должна доходить до заявки.

---

# 9. Доставка

Актуальное правило доставки:

- внутри МКАД: 6000 ₽;
- за пределами МКАД: +50 ₽/км.

Доставка не входит в стоимость изделия.

Она добавляется отдельной строкой, если пользователь выбирает доставку.

---

# 10. Сборка

Актуальное правило сборки:

```text
сборка = 10% от стоимости изделия без учёта доставки
```

Сборка не входит в стоимость изделия.

Она добавляется отдельной строкой, если пользователь выбирает сборку.

---

# 11. Price snapshot

## 11.1 Назначение

Price snapshot нужен, чтобы заказ был воспроизводимым.

Если цены в Supabase изменились позже, исторический заказ всё равно должен сохранять цену, с которой пользователь отправил заявку.

## 11.2 Что сохранять

Price snapshot должен хранить:

- order id;
- timestamp;
- product price;
- delivery price;
- assembly price;
- total price;
- source of catalog;
- material selection;
- hardware selection;
- applied coefficients;
- pricing version;
- config reference;
- production model reference.

## 11.3 Где используется

Price snapshot используется:

- в заявке;
- в личном кабинете;
- в админке;
- в email;
- для аудита;
- для повторной проверки.

---

# 12. Client price и server price

Система должна различать:

- client-calculated price;
- server-resolved price.

Server price является более доверенным источником.

Админ должен видеть расхождение, если оно есть.

Пользователь не должен видеть техническое сравнение client/server.

---

# 13. Связь с Constructor

Pricing пересчитывается при изменении:

- типа мебели;
- размеров;
- секций;
- наполнения;
- материалов;
- фасадов;
- фурнитуры;
- опор;
- доставки;
- сборки.

Constructor не должен сам быть окончательным источником цены. Он может показывать рассчитанную цену, но итоговая заявка должна проходить server-side validation/price snapshot.

---

# 14. Связь с Production JSON

Цена должна считаться из той же модели, из которой формируется Production JSON.

Запрещённая ситуация:

```text
Constructor показывает одно
Pricing считает второе
Production JSON описывает третье
```

Все три слоя должны быть согласованы.

---

# 15. Связь с Supabase

Supabase должен хранить runtime catalog, но Pricing Engine не должен ломаться, если Supabase временно недоступен в development/staging.

Для production нужно определить строгую policy:

- можно ли принимать заявки при fallback;
- как логировать fallback;
- как показывать статус администратору.

Окончательное production-правило требует отдельного решения.

---

# 16. Связь с Admin

Админка должна видеть:

- цену изделия;
- доставку;
- сборку;
- итоговую сумму;
- price snapshot;
- источник цены;
- client/server mismatch;
- pricing version.

Админка должна помогать понять, почему цена такая, но не обязана быть бухгалтерской системой на MVP.

---

# 17. Связь с личным кабинетом

Клиент в личном кабинете видит:

- стоимость изделия;
- доставку;
- сборку;
- итог;
- параметры заказа;
- материалы в клиентском виде.

Клиент не видит:

- внутреннюю себестоимость;
- price source internals;
- коэффициенты;
- server/client mismatch;
- подробную production калькуляцию.

---

# 18. Маржа

На текущем этапе отдельная маржа по материалам, фурнитуре и услугам не вводится.

Используется общая коммерческая логика через коэффициент и текущие правила расчёта.

Будущая маржинальная модель может быть добавлена позже, но она должна быть отражена в RPES и backlog до реализации.

---

# 19. Валидация Pricing

Цена считается валидной, если:

- все материалы найдены;
- все фурнитурные элементы имеют цену или допустимый fallback;
- production model валидна;
- delivery/assembly рассчитаны по правилам;
- price snapshot сформирован;
- server price успешно resolved;
- нет критических расхождений.

Если цена невалидна, заявка не должна быть отправлена.

---

# 20. Ошибки Pricing

Пользователь должен видеть простое сообщение:

- «Не удалось рассчитать цену. Проверьте параметры или попробуйте позже».

Пользователь не должен видеть:

- Supabase error;
- missing SKU;
- seed fallback reason;
- internal pricing exception;
- stack trace.

Админ должен видеть техническую причину в безопасном виде.

---

# 21. Инварианты Pricing

1. Цена должна быть точной.
2. Стоимость изделия не включает доставку и сборку.
3. Доставка и сборка считаются отдельными строками.
4. В заказе сохраняется price snapshot.
5. Server price важнее client price.
6. Client/server mismatch должен быть виден админу.
7. Клиент не видит внутреннюю калькуляцию.
8. Цена должна быть связана с Production JSON.
9. Невалидная цена блокирует заявку.
10. Supabase catalog нужен до MVP.
11. SKU нужны до MVP.
12. Остатки материалов пока не учитываются.

# 24. Дополнительные решения Pricing v1.1

## 24.1 Материал в Supabase как обязательный источник

Материал, выбранный в конструкторе, должен существовать в Supabase.

Нельзя использовать материал, которого нет в Supabase catalog, для новых заявок.

## 24.2 Если материал удалён или недоступен

Для старых проектов сохраняется исторический snapshot.

Для новых заявок материал недоступен.

В админку должна попадать проблема каталога.

## 24.3 Manager price override

Админ/менеджер может вручную изменить цену.

Это изменение должно быть:

- явно зафиксировано;
- отображено в истории;
- отделено от автоматически рассчитанной цены;
- доступно в админке.

Клиенту показывается актуальная согласованная цена, но внутренне нужно хранить историю изменения.

## 24.4 Скидки и промокоды

Скидки/промокоды нужны.

Их правила требуют отдельного проектирования:

- тип скидки;
- размер;
- область применения;
- срок действия;
- кто может выдать;
- как отображается клиенту;
- как хранится в price snapshot.

## 24.5 Округление

Цена округляется до 1 рубля.

## 24.6 Упаковка

Упаковка считается на 1 кв.м листового материала, используемого в проекте.

Нужно отдельно определить стоимость упаковки за 1 кв.м.

## 24.7 Client/server mismatch

Если client price и server price расходятся, заявка создаётся с server price.

Админ должен видеть факт расхождения.

## 24.8 Server price priority

Server price является финальным источником цены при создании заявки.

Client price используется для UX и предварительного отображения в интерфейсе, но финальная заявка должна сохранять server-resolved price.
