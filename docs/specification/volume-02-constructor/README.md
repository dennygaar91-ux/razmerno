# 1. Назначение тома

Этот том описывает конструктор как центральный продуктовый и инженерный модуль «Размерно».

Конструктор — это не форма сбора параметров и не простой визуальный конфигуратор. Это основной интерфейс, через который пользователь самостоятельно создаёт мебель, а система преобразует его действия в валидную производственную модель, точную цену, заявку и последующее отображение в личном кабинете и админке.

Том фиксирует:

- шаги конструктора;
- пользовательскую логику;
- режимы работы;
- связь с Three.js;
- связь с Pricing;
- связь с Production JSON;
- связь с авторизацией;
- связь с личным кабинетом;
- правила валидации;
- продуктовые инварианты;
- открытые вопросы и будущие backlog-задачи.

---

# 2. Роль конструктора в продукте

Конструктор — ядро продукта «Размерно».

Лендинг объясняет ценность продукта, но реальная ценность возникает в момент, когда пользователь сам начинает собирать мебель.

Главное ощущение, которое должен дать конструктор:

> Я сам могу собрать мебель под свои размеры, и система не даст мне ошибиться.

Это означает, что конструктор должен одновременно быть:

- простым для новичка;
- достаточно гибким для DIY-пользователя;
- визуальным;
- производственно корректным;
- связанным с точной ценой;
- связанным с заявкой;
- связанным с личным кабинетом;
- связанным с админкой и production layer.

---

# 3. Главный пользовательский путь

Основной путь:

```text
Открытие конструктора
→ выбор типа мебели
→ ввод размеров
→ настройка наполнения
→ выбор материалов
→ проверка валидности
→ активация кнопки «Отправить заявку»
→ проверка авторизации
→ авторизация при необходимости
→ возврат к сохранённой конфигурации
→ создание заявки
→ номер заявки
→ переход в личный кабинет
→ просмотр заказа
```

## Инварианты пути

1. Конфигурация не теряется.
2. Невалидная конфигурация не отправляется.
3. Авторизация не требуется до попытки отправить заявку.
4. Заявка создаётся только после успешной проверки конфигурации.
5. Заявка связана с пользователем.
6. Заявка воспроизводима.
7. Цена сохраняется как snapshot.
8. Production model сохраняется как snapshot.
9. Клиент не видит внутренний Production JSON.

# 4. Шаги конструктора

Актуальные шаги:

1. Тип мебели.
2. Размеры.
3. Наполнение.
4. Материалы.

Заявка не является шагом конструктора.

Заявка — отдельное действие, которое становится доступным только после успешной валидации.

## Почему заявка не является шагом

Заявка связана не только с настройкой мебели, но и с:

- авторизацией;
- сохранением проекта;
- созданием заказа;
- личным кабинетом;
- email-уведомлением;
- price snapshot;
- production model snapshot.

Поэтому её нельзя рассматривать как простой шаг wizard.

---

# 5. Шаг «Тип мебели»

## 5.1 Назначение

Пользователь выбирает, какой тип мебели он собирает.

MVP-типы:

- шкаф;
- тумба;
- комод.

## 5.2 UX-правило

Выбор типа мебели должен происходить в Three.js-сцене.

Панель может дублировать выбор, но первый смысловой контакт пользователя с типом мебели должен быть визуальным.

## 5.3 Почему это важно

Пользователь должен сразу почувствовать, что «Размерно» — это визуальный конструктор, а не форма с полями.

3D-сцена должна с первого шага показать, что пользователь работает с мебелью, а не с абстрактными настройками.

## 5.4 Влияние типа мебели

Выбор типа мебели влияет на:

- правила корпуса;
- доступные размеры;
- правила верхней панели;
- правила фасадов;
- доступное наполнение;
- опоры;
- фурнитуру;
- production JSON;
- pricing;
- Basis manual plan.

## 5.5 При смене типа мебели

Если пользователь меняет тип мебели после настройки, система должна:

1. проверить совместимость текущей конфигурации;
2. сохранить всё, что можно сохранить;
3. сбросить только несовместимые параметры;
4. объяснить это простым языком.

Нельзя молча уничтожать конфигурацию.

# 6. Шаг «Размеры»

## 6.1 Назначение

Пользователь задаёт габариты мебели и/или секций.

## 6.2 Главный принцип

Моделирование должно опираться на секции, а не только на общий размер изделия.

Это позволяет избежать категории «нестандартный размер». Если изделие собирается из допустимых секций, оно считается валидным.

## 6.3 Ограничения секции

- ширина: 200–900 мм;
- высота: 200–2000 мм;
- глубина: 150–900 мм.

## 6.4 Высота и опоры

Высота изделия включает высоту опор.

```text
общая высота изделия = высота корпуса + высота опор
```

Это правило должно быть единым для конструктора, pricing, production model, личного кабинета и админки.

## 6.5 UX ввода размеров

Пользователь не должен думать о технологических вычетах.

Он вводит понятные размеры:

- ширина;
- высота;
- глубина.

Система сама рассчитывает:

- размеры корпуса;
- высоту опор;
- размеры панелей;
- допустимость секций;
- производственные ограничения.

## 6.6 Ошибки размеров

Система должна предотвращать:

- слишком узкие секции;
- слишком широкие секции;
- слишком маленькую высоту;
- слишком большую высоту;
- недопустимую глубину;
- конфигурации, в которых наполнение невозможно разместить.

Ошибки должны объясняться простым языком.

---

# 7. Шаг «Наполнение»

## 7.1 Назначение

Пользователь определяет внутреннюю структуру мебели.

MVP-элементы:

- полки;
- ящики;
- штанги.

## 7.2 Секции, отсеки и зоны

Текущая рабочая терминология:

- секция — крупный строительный блок мебели;
- отсек — внутренняя часть секции;
- зона — интерактивная область в 3D, с которой может работать пользователь.

Терминология требует финального уточнения, но в продукте должно быть единое словоупотребление.

## 7.3 Добавление секций

Секции могут добавляться:

- влево;
- вправо;
- вверх.

Добавление секций вверх — стратегическое решение, которое переводит модель из простой горизонтальной схемы в более гибкую модульную сетку.

## 7.4 Обычный режим наполнения

В обычном режиме пользователь работает через простые controls:

- количество полок;
- количество ящиков;
- наличие штанги;
- пресеты.

Обычный режим не должен требовать знания секционной логики.

## 7.5 Точная настройка наполнения

В точной настройке пользователь работает через Three.js:

1. выбирает секцию;
2. выбирает отсек/зону;
3. выбирает действие;
4. задаёт параметры;
5. система валидирует действие;
6. модель обновляется.

## 7.6 Добавление полки

Сценарий:

```text
Выбор секции
→ Добавить
→ Полка
→ Ввести расстояние от нижней панели
→ Проверка значения
→ Добавление полки
→ Обновление 3D
→ Обновление pricing
→ Обновление production model
```

## 7.7 Инварианты наполнения

- Наполнение не может нарушать производственные правила.
- Любой элемент наполнения должен попасть в production JSON.
- Любой элемент наполнения должен влиять на цену.
- Любой элемент наполнения должен быть воспроизводим в личном кабинете и админке.
- Пользователь не должен отправить конфигурацию, где элементы физически не помещаются.

---

# 8. Шаг «Материалы»

## 8.1 Назначение

Пользователь выбирает внешний и конструкционный вид мебели.

## 8.2 Уровни выбора материала

Материалы могут задаваться:

1. на уровне изделия;
2. на уровне фасадов;
3. на уровне отдельной панели в режиме точной настройки.

## 8.3 Panel-level material override

Пользователь должен иметь возможность изменить материал отдельной панели, например левой боковины.

Это относится к точной настройке.

## 8.4 Производственные правила материалов

Корпус:

- ЛДСП 16 мм.

Фасады:

- ЛДСП 16 мм;
- МДФ 18 мм.

Задняя стенка:

- ХДФ.

Дно ящика:

- ХДФ.

## 8.5 Направление текстуры

- если ширина панели больше высоты — горизонтально;
- иначе вертикально;
- ХДФ без направления.

## 8.6 Инварианты материалов

- Материал должен соответствовать роли панели.
- Материал должен влиять на цену.
- Материал должен отображаться в 3D.
- Материал должен попадать в production JSON.
- Материал должен сохраняться в личном кабинете.
- Материал должен быть доступен администратору.

---

# 9. Режимы конструктора

## 9.1 Обычный режим

Обычный режим предназначен для большинства пользователей.

Характеристики:

- простые controls;
- минимум технических терминов;
- понятные пресеты;
- подсказки;
- автоматические проверки;
- низкий когнитивный порог.

## 9.2 Точная настройка

Точная настройка предназначена для пользователей, которым нужен более детальный контроль.

Возможности:

- выбор конкретной панели;
- изменение материала панели;
- выбор секции;
- выбор зоны;
- добавление элемента в конкретное место;
- точная высота полки;
- точное управление наполнением.

## 9.3 Ограничения точной настройки

Точная настройка не должна превращаться в CAD.

Запрещено показывать:

- присадку;
- пазы;
- кромку;
- координаты;
- внутренний JSON;
- технические чертежи.

## 9.4 Объяснение невозможных действий

Если действие невозможно, система объясняет это простым языком:

- «Секция слишком узкая для ящика».
- «Полка не помещается на выбранной высоте».
- «Для этой глубины нельзя добавить штангу».
- «Материал недоступен для фасада».

# 10. Заявка и авторизация

## 10.1 Активация заявки

Кнопка «Отправить заявку» активируется только если:

- выбран тип мебели;
- размеры валидны;
- наполнение валидно;
- материалы валидны;
- цена рассчитана;
- production model валидна.

## 10.2 Авторизация после нажатия

Авторизация происходит только после нажатия «Отправить заявку».

Если пользователь не авторизован:

```text
Отправить заявку
→ Авторизация
→ Возврат к конфигурации
→ Создание заявки
→ Номер заявки
→ Личный кабинет
```

Если пользователь авторизован:

```text
Отправить заявку
→ Создание заявки
→ Номер заявки
→ Личный кабинет
```

## 10.3 Инварианты заявки

- Невалидная конфигурация не отправляется.
- Конфигурация не теряется.
- Заявка получает номер.
- Заявка связана с пользователем.
- Сохраняется price snapshot.
- Сохраняется production model snapshot.
- Клиент может просмотреть заказ в личном кабинете.

---

# 11. Связь с Pricing

Цена должна пересчитываться при изменении:

- типа мебели;
- размеров;
- секций;
- наполнения;
- материалов;
- фасадов;
- фурнитуры;
- опор.

Клиенту показывается:

- стоимость изделия;
- доставка;
- сборка.

Не показывается:

- стоимость каждой панели;
- стоимость каждой фурнитуры;
- внутренняя production breakdown.

---

# 12. Связь с Production JSON

Любое действие конструктора должно быть отражаемо в production model.

Примеры:

- изменение размера → изменение панелей;
- добавление полки → новая панель;
- добавление ящика → панели ящика, фасад, направляющие;
- выбор без ручек → push-to-open;
- изменение материала панели → materialRef override.

Инвариант:

> Если действие нельзя корректно отразить в production model, оно не должно быть валидным действием.

---

# 13. Связь с личным кабинетом

Личный кабинет должен показывать клиентскую версию проекта:

- параметры;
- материалы;
- цену;
- статус;
- номер заявки;
- историю;
- понятный production summary.

Не показывать:

- внутренний JSON;
- присадку;
- кромку;
- пазы;
- технические warnings.

---

# 14. Связь с админкой

Админка получает только валидные заявки.

Админка должна видеть:

- заявку;
- цену;
- customer data;
- production summary;
- Basis status;
- email status;
- статус заказа;
- возможные внутренние проблемы.

# 15. Ошибки и предупреждения

## 15.1 Главный принцип

Ошибки должны предотвращаться на клиентском пути.

## 15.2 Что блокирует заявку

- не выбран тип мебели;
- размеры невалидны;
- наполнение невозможно;
- материал не подходит;
- production model невалидна;
- цена не рассчитана;
- обязательные данные отсутствуют.

## 15.3 Что можно показывать как warning

Warnings можно показывать, если пользователь может продолжить настройку.

Но кнопка отправки заявки активна только при полностью валидной конфигурации.

# 19. Решения v1.1 по размерам, секциям и предотвращению ошибок

## 19.1 Изменение общего размера изделия

При изменении общего размера изделия система не должна молча ломать уже настроенную структуру секций.

Актуальное решение:

после изменения общего размера пользователь получает выбор:

1. распределить изменение равномерно;
2. сохранить размеры секций, если это возможно;
3. выбрать вручную, какие секции изменить.

Это правило особенно важно для сценариев, где пользователь уже вручную настроил секции, зоны, полки, материалы отдельных панелей или наполнение.

## 19.2 Почему выбран такой сценарий

Автоматическое пропорциональное масштабирование может сломать ручную настройку.

Автоматическое сохранение размеров секций может создать лишнее пространство.

Поэтому лучший UX — дать пользователю понятный выбор в момент изменения размера, но не перегружать его заранее.

## 19.3 Добавление секций справа и сверху

Секции можно добавлять:

- справа;
- сверху.

При моделировании и формировании JSON фундаментальное правило координат:

> координаты начинаются с левого нижнего дальнего угла.

Это правило должно быть единым для конструктора, Three.js, Production JSON и Basis manual plan.

## 19.4 Вертикальное добавление секций

Актуальное решение — вариант C:

- добавление сверху работает как добавление новой строки/уровня;
- при этом пользователь позже может увеличить ширину верхней секции независимо от нижней;
- нижняя секция при этом не обязана менять свою ширину.

Это означает, что секционная модель должна поддерживать не только простую равномерную сетку, но и независимые размеры верхних и нижних секций при сохранении корректной координатной системы.

## 19.5 Глубина секций

На текущем этапе глубина всех секций внутри одного изделия должна быть одинаковой.

Разная глубина секций откладывается, потому что она усложняет:

- верхние панели;
- задние стенки;
- фасады;
- Three.js;
- Pricing;
- Production JSON;
- Basis manual plan.

## 19.6 Ограничения секций как UX-защита

Система не должна давать пользователю выбрать ошибочный вариант.

Если секция выходит за допустимые пределы, действие должно быть недоступно или не применяться.

Минимальная ширина секции: 200 мм.  
Максимальная ширина секции: 900 мм.

## 19.7 Ограничение по полкам

Минимальная высота между полками: 300 мм.

Это правило должно использоваться в:

- обычном режиме;
- точной настройке;
- пресетах;
- validation;
- Production JSON;
- Pricing.

## 19.8 Технический долг: пресеты наполнения

Нужно отдельно проработать большую систему пресетов:

- где по умолчанию ставятся полки;
- где по умолчанию ставятся ящики;
- где ставится штанга;
- какие расстояния используются;
- какие сценарии считаются удобными;
- какие сценарии производственно корректны.

Этот блок должен стать отдельным backlog epic: `Filling Presets & Placement Logic`.
