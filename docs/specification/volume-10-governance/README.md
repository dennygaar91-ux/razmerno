
# RPES — Том X. Governance & Development Rules

Проект: «Размерно»
Версия: 1.1 draft

# 1. Назначение

Этот том определяет правила разработки, принятия решений, контроля качества и управления проектом.

Это главный организационный Source of Truth.

---

# 2. Главные принципы

1. Решения принимаются один раз и фиксируются в RPES.
2. Новые решения могут заменить старые только явным продуктовым решением.
3. Backlog обязан соответствовать RPES.
4. Код обязан соответствовать RPES.
5. Если код противоречит RPES — исправляется код либо официально меняется RPES.

---

# 3. Source of Truth

Приоритет документов:

1. RPES.
2. Product Backlog.
3. Git main.
4. Остальная документация.

Никакие старые обсуждения не могут иметь приоритет над RPES.

---

# 4. Работа с backlog

Каждая задача должна иметь:

- идентификатор;
- описание;
- критерии готовности;
- зависимости;
- приоритет;
- статус;
- evidence.

Статусы:

- Planned
- In Progress
- Blocked
- Review
- QA
- Done

Закрывать задачу без evidence запрещено.

---

# 5. Правила разработки

Разработка ведётся небольшими безопасными изменениями.

Запрещено без необходимости:

- массовый рефакторинг;
- изменение package-lock;
- изменение API без контракта;
- изменение production runtime без тестов.

Любое изменение должно иметь понятный scope.

---

# 6. Definition of Ready

Задача готова к разработке, если:

- цель понятна;
- критерии определены;
- зависимости известны;
- архитектурных противоречий нет.

---

# 7. Definition of Done

Задача считается завершённой только если:

- код реализован;
- тесты проходят;
- typecheck проходит;
- build проходит;
- документация обновлена;
- backlog обновлён;
- имеются evidence;
- нет известных регрессий.

---

# 8. QA

Минимальный QA:

- unit;
- contract;
- regression;
- ручная проверка ключевого сценария.

Для продуктовых функций дополнительно:

- UX проверка;
- согласованность с RPES.

---

# 9. Git Flow

Рекомендуемый цикл:

main
→ feature branch
→ commit
→ QA
→ PR
→ review
→ merge
→ verification
→ backlog update

---

# 10. Правила для AI

Codex используется для реализации.

Cursor может выполнять крупные инженерные задачи.

ChatGPT отвечает за:

- архитектуру;
- продуктовые решения;
- RPES;
- backlog;
- аудит;
- QA-анализ;
- подготовку заданий.

Любое решение сначала отражается в RPES.

---

# 11. Архитектурные stop conditions

Требуют отдельной проверки:

- package.json;
- package-lock.json;
- API;
- pricing;
- Supabase;
- production runtime;
- GitHub Actions;
- workflow;
- большие diff.

---

# 12. Документация

После изменения продукта обновляются:

- RPES;
- backlog;
- при необходимости roadmap.

Документация считается частью продукта.

---

# 13. Release Readiness

Перед релизом обязательно:

- все критические backlog задачи закрыты;
- RPES актуален;
- Production JSON валиден;
- Pricing совпадает;
- личный кабинет работает;
- админка работает;
- авторизация работает;
- build зелёный;
- тесты зелёные.

---

# 14. Инварианты

1. RPES — главный источник требований.
2. Backlog не противоречит RPES.
3. Нельзя закрывать задачи без evidence.
4. Любая функция проходит QA.
5. Любое изменение должно быть воспроизводимым.
6. Архитектурные решения документируются.
7. Production correctness важнее скорости разработки.
8. Пользователь не должен получать невалидную конфигурацию.

---

# 15. Следующее развитие RPES

# 16. Решения Release v1.1

## 16.1 MVP фактически является Release v1

Текущий объём продукта больше, чем лёгкий MVP.

Поэтому рабочее название:

> Release v1

А не «сырой MVP».

## 16.2 Допустимое сокращение scope

Если реализация всех трёх типов мебели слишком замедлит запуск, можно временно сократить scope до шкафа.

Приоритет:

1. шкаф;
2. тумба;
3. комод.

Но текущая целевая позиция — оставить все три типа, пока это возможно.

## 16.3 Онлайн-оплата

Онлайн-оплата не входит в MVP/Release v1.

## 16.4 Юридические документы

Для запуска нужны:

- оферта;
- политика обработки персональных данных;
- согласие на обработку персональных данных.

## 16.5 Критерий запуска

Release v1 готов, если работает полноценный сценарий:

```text
Главная
→ конструктор
→ валидная конфигурация
→ авторизация
→ заявка
→ личный кабинет
→ админка
→ price snapshot
→ production snapshot
→ email
```

Если тумба и комод задерживают запуск, решение о сокращении scope принимается отдельно и фиксируется в RPES.
