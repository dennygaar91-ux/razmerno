# 2. Что такое «Размерно»

«Размерно» — сервис самостоятельного проектирования, конфигурирования и заказа мебели по индивидуальным размерам.

Пользователь самостоятельно собирает мебель под своё помещение без посредников, без ожидания расчётов от разных мебельщиков и без необходимости разбираться в сложных технических деталях мебельного производства.

Главная продуктовая формула:

> Собрать мебель самому — как понятный конструктор.

При этом продукт не является игрушечным конфигуратором. Внутри должна работать строгая производственная модель: материалы, панели, кромка, фурнитура, пазы, присадка, JSON, Basis manual plan, pricing и validation.

Для пользователя всё это остаётся под капотом.

# 3. Философия продукта

## 3.1 Пользователь проектирует мебель, а не производство

Пользователь должен мыслить категориями:

- шкаф;
- тумба;
- комод;
- секция;
- отсек;
- полка;
- ящик;
- фасад;
- материал;
- ручки;
- сборка.

Пользователь не должен мыслить категориями:

- присадка;
- кромка;
- пазы;
- координаты сверления;
- Basis JSON;
- технологические карты;
- производственные warning-коды.

## 3.2 Производственная сложность скрыта

Система может быть очень сложной внутри, но клиентский интерфейс должен оставаться простым. Если сложность можно автоматизировать — она автоматизируется. Если сложность требует технолога — её видит админ/технолог, но не клиент.

## 3.3 Корректность важнее иллюзии свободы

Пользователь должен чувствовать свободу настройки, но система не должна позволять создать невалидную мебель.

Если действие невозможно произвести корректно, оно не должно быть доступно как валидное действие.

## 3.4 Ошибки нужно предотвращать заранее

Продукт не должен строиться по принципу «пользователь ошибся → потом менеджер исправит». Цель — не допустить ошибочную заявку.

Заявка должна отправляться только при полностью валидной конфигурации.

## 3.5 Конструктор должен вести пользователя

Пользователь не обязан знать, как проектируется мебель. Система должна вести его пошагово, объяснять действия простым языком и автоматически выполнять технические проверки.

# 4. Позиционирование

## 4.1 Основная формулировка

«Размерно» — сервис, который позволяет самостоятельно собрать мебель под свои размеры без посредников, сложностей и долгого ожидания расчётов.

## 4.2 Основной акцент

В коммуникации нужен перекос в сторону:

- собрать самому;
- как конструктор;
- без посредников;
- без технической сложности;
- под точные размеры;
- с понятной стоимостью;
- с понятной сборкой.

## 4.3 Что продаёт продукт

«Размерно» продаёт не просто мебель.

Он продаёт ощущение:

> Я сам смог собрать мебель именно под своё пространство.

## 4.4 Основные обещания

1. Пользователь сам управляет конфигурацией.
2. Мебель создаётся под точные размеры.
3. Цена считается прозрачно и точно.
4. Сборка должна быть понятной.
5. Производственная корректность обеспечивается системой.
6. Не нужно ждать множество расчётов от мебельщиков.
7. Не нужно разбираться в сложных технических деталях.

# 5. Отличие от альтернатив

## 5.1 Отличие от обычной мебели на заказ

Обычная мебель на заказ часто требует общения с разными исполнителями и даёт большой разброс стоимости. Один и тот же шкаф может получить цену с разницей в несколько раз.

«Размерно» убирает неопределённость:

- пользователь сам собирает конфигурацию;
- цена считается сразу;
- параметры прозрачны;
- логика заказа единая;
- итоговая модель воспроизводима.

## 5.2 Отличие от серийной мебели

Серийная мебель не создаётся под точные размеры пользователя. Она часто имеет универсальную конструкцию и компромиссы.

«Размерно» создаёт мебель под конкретные размеры, не превращая пользователя в технолога.

## 5.3 Отличие от CAD и БАЗИС

«Размерно» не является CAD-системой и не заменяет БАЗИС-Мебельщик.

БАЗИС и производственные детали остаются внутри производственного слоя. Пользователь работает с мебелью, а не с чертежами.

# 6. Целевая аудитория

## 6.1 Обычный пользователь

Пользователь без опыта проектирования мебели.

Ему важно:

- понять, что делать;
- не ошибиться;
- увидеть результат;
- получить точную цену;
- понять, что сборка возможна.

## 6.2 DIY-пользователь

Пользователь, который хочет больше контроля.

Ему важно:

- менять секции;
- управлять наполнением;
- менять материалы отдельных панелей;
- использовать точную настройку;
- видеть реалистичный результат.

## 6.3 Общий принцип

Один продукт должен обслуживать обе группы.

Обычный путь — простой и пошаговый.

Расширенный путь — через режим «Точная настройка».

# 7. Главные боли клиента

1. Непрозрачная цена.
2. Большой разброс стоимости у разных производителей.
3. Страх ошибиться в размерах.
4. Непонимание, как будет выглядеть мебель.
5. Страх сложной сборки.
6. Сомнение в правильности деталей.
7. Долгое ожидание расчёта.
8. Необходимость общаться с посредниками.
9. Сложные технические термины.
10. Сложность сравнения предложений.
11. Невозможность получить мебель точно под своё пространство без лишних переговоров.

---

# 8. Причины оставить заявку

Пользователь должен оставить заявку, если он понял:

1. Продуктом легко пользоваться.
2. Это выгодно и прозрачно.
3. Сборка выглядит понятной.
4. Конфигурация валидна.
5. Цена точная.
6. После заявки он сможет увидеть заказ и детали в личном кабинете.

---

# 9. Основной пользовательский путь

```text
Главная
→ Конструктор
→ Тип мебели
→ Размеры
→ Наполнение
→ Материалы
→ Валидная конфигурация
→ Отправить заявку
→ Проверка авторизации
→ Авторизация при необходимости
→ Возврат к конфигурации
→ Создание заявки
→ Номер заявки
→ Личный кабинет
→ Просмотр заказа
```

## Инварианты пути

- Конфигурация не теряется при авторизации.
- Невалидная конфигурация не отправляется.
- Заявка связана с пользователем.
- Заявка воспроизводима.
- В заказе сохраняется price snapshot.
- В заказе сохраняется production model snapshot.
- Клиент не видит технический JSON.

# 10. MVP

## 10.1 Принцип MVP

MVP «Размерно» не должен быть сырым полупродуктом. Это должен быть полноценный сервис с ограниченным ассортиментом, но с рабочим пользовательским циклом.

## 10.2 Обязательный состав MVP

MVP должен включать:

- главную страницу;
- конструктор;
- Three.js;
- выбор типа мебели;
- размеры;
- наполнение;
- материалы;
- авторизацию;
- личный кабинет;
- админку;
- точную цену;
- Production JSON;
- Supabase material catalog;
- SKU;
- Basis manual export;
- заявки;
- email;
- корректный UI/UX;
- полноценную мобильную версию;
- стабильную сборку;
- валидную production model.

## 10.3 Что нельзя выпускать без

Нельзя выпускать MVP без:

- Supabase material catalog;
- Production v4 runtime;
- SKU;
- полноценной мобильной версии;
- авторизации;
- личного кабинета;
- корректного UI/UX;
- валидного JSON;
- точной цены;
- рабочего admin flow.

## 10.4 Post-MVP

После MVP:

- другие виды мебели;
- B2B;
- кухни;
- AI assembly;
- автоматизация Basis;
- расширенная производственная автоматизация.

# 11. Инварианты продукта

1. Пользователь не видит производственную сложность.
2. Пользователь не видит присадку, кромку, пазы и внутренний JSON.
3. Любая отправленная заявка валидна.
4. Конфигурация не теряется при авторизации.
5. Цена точная.
6. Заявка полностью воспроизводима.
7. Production model является внутренним источником истины.
8. Three.js является основным рабочим интерфейсом.
9. Ошибочные заявки не попадают в админку.
10. Личный кабинет обязателен.
11. Авторизация нужна после попытки отправить заявку, а не заранее.
12. Пользователь выбирает производителя фурнитуры, но не конкретную модель.
13. Если новое решение конфликтует со старым, актуальным считается новое решение, зафиксированное в RPES.

# 12. Критерии качества

## 12.1 UX

Хороший UX означает:

- пользователь понимает следующий шаг;
- интерфейс не перегружен;
- производственная сложность скрыта;
- ошибки предотвращаются;
- 3D помогает, а не мешает;
- мобильная версия полноценна.

## 12.2 Pricing

Хороший pricing означает:

- цена точная;
- источник цены понятен системе;
- price snapshot сохраняется;
- доставка и сборка считаются отдельно;
- клиенту не показывают ненужную детализацию.

## 12.3 Production

Хорошая production model означает:

- модель валидна;
- все панели, материалы, кромка, фурнитура и пазы отражены;
- JSON достаточен для ручной подготовки в БАЗИС;
- клиент не видит технические детали.

## 12.4 Admin

Хорошая админка означает:

- видны заявки;
- видны статусы;
- видны цены;
- видны проблемы;
- можно экспортировать JSON/PDF;
- доступны данные клиента;
- нет лишнего PII в логах.

# 14. Дополнительные продуктовые решения v1.1

## 14.1 Конструктор как система предотвращения ошибок

Конструктор должен быть устроен так, чтобы пользователь не мог выбрать ошибочный вариант.

Это один из главных принципов продукта: система не должна позволять пользователю собрать невалидную конфигурацию, а затем показывать ошибку на финальном этапе. Ограничения должны быть встроены в интерфейс заранее.

Примеры:

- нельзя выбрать секцию меньше допустимого размера;
- нельзя добавить полку, если высота между полками будет меньше минимума;
- нельзя выбрать материал, которого нет в Supabase-каталоге;
- нельзя выбрать недоступную комбинацию ручек/фурнитуры;
- нельзя отправить заявку, если production model невалидна.

## 14.2 Material catalog as product truth

Материал в конструкторе должен быть материалом из Supabase.

Принцип:

> Материал в интерфейсе = материал в Supabase catalog.

Нельзя показывать пользователю материал, которого нет в актуальном каталоге Supabase. Если материала нет в Supabase, он не должен быть доступен для новых конфигураций.

## 14.3 Production v4 as final production engine

Production v4 должен заменить v3 после controlled migration.

Долгосрочно система не должна поддерживать два production engine одновременно. v3 может существовать только как временный переходный слой до полной миграции.

Целевое состояние:

```text
Production v4 = единственный production runtime
Production v3 = deprecated / removed after migration
```
